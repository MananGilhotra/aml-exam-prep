Stochastic & Mini-Batch
Gradient Descent

Why Batch GD waits so long, how SGD gets moving from a single sample, and how Mini-Batch gives you the best of both.

⏱ ~35 min🔁 3 dry runs 💻 3 pseudocodes✓ 10 MCQs
⚡ Ek Line Mein

Batch GD: the average gradient over the whole dataset → 1 update per epoch, accurate but slow. SGD: the gradient of one random sample → $m$ updates per epoch, fast but noisy. Mini-Batch: the average over $b$ samples → $\lceil m/b\rceil$ updates per epoch — the practical compromise that almost every real system actually uses.

Notation used throughout

$d$number of features (parameter dimension)

$J_i(\boldsymbol\theta)$loss from a single training example $i$

1Revision and Motivation

▷ Hook

In Batch Gradient Descent we compute the gradient of the average cost over all $m$ examples and then update $\boldsymbol\theta$ once. The rhythm is: scan all the samples → average their gradients → update once. Must we always wait for the entire dataset before a single update?

If $m = 10{,}000{,}000$, how many parameter updates happen in one BGD epoch? One. Is a single update worth scanning 10 million samples every time?

Why BGD is attractive

  • Stable direction: every sample contributes, so noisy gradients average out.
  • Deterministic path: the steps are exactly repeatable for the same initialisation.
  • Smooth convergence: on simple convex losses the cost usually falls smoothly.
  • Good for small datasets: exact gradients are affordable when the data fits in memory.

2Stochastic Gradient Descent (SGD)

? Think & Discuss

Computing the full gradient is expensive. What is the smallest amount of data that could still give a direction to move $\boldsymbol\theta$ in? A single sample. And that choice immediately creates a new danger — noise.

SGD is the answer to the waiting problem. Instead of asking the whole dataset for one perfect direction, SGD asks one randomly chosen example for a quick direction and updates immediately.

Analogy

Batch GD polls the entire class before making any decision. SGD asks one random student, acts on their answer immediately, then asks the next. Any single answer might be off, but decisions happen instantly instead of after a full roll call.

Core intuition

Each training example offers a small opinion about how $\boldsymbol\theta$ should move. A single opinion may be biased, but if selected randomly, many opinions average towards the full-data direction. SGD does not change the loss function — it only changes how we estimate the gradient before each update.

The stochastic update $$i_t \sim \text{Uniform}\{1, 2, \dots, m\}, \qquad \mathbf g_t = \nabla J_{i_t}(\boldsymbol\theta_t), \qquad \boldsymbol\theta_{t+1} = \boldsymbol\theta_t - \alpha\,\mathbf g_t$$
  • $J_{i_t}$ — the loss of the training example selected at iteration $t$
  • $\nabla J_{i_t}$ — the gradient for that example (a vector of loss slopes)
  • $\boldsymbol\theta_t$ — the current parameter vector at which the gradient is evaluated
  • $\mathbf g_t = \nabla J_{i_t}(\boldsymbol\theta_t)$ — the selected example's gradient, computed at the current parameters
★ Key Insight — the biggest misconception

SGD is not training on just one sample forever! One update uses one sample, but one epoch uses every sample. If $m = 1000$, one SGD epoch contains 1000 updates.
After $E$ full epochs SGD has made $E \times m$ updates in total — compare that to Batch GD's mere $E$ updates over the same $E$ epochs.

Complete SGD workflow

  1. Initialize $\boldsymbol\theta$. Choose the learning rate $\alpha$ and the number of epochs.
  2. At the start of each epoch, shuffle the training examples.
  3. Visit the samples one by one in the shuffled order.
  4. For each sample compute the prediction, sample loss and sample gradient, and update $\boldsymbol\theta$ immediately.
  5. Repeat for multiple epochs, tracking the training (or validation) loss trend as you go.
△ Warning — SHUFFLING

Real datasets are often ordered (by date, by class label, by region). Without shuffling, consecutive SGD updates can follow the ordering pattern instead of the true learning signal. Randomisation is what protects SGD from biased updates!

Effect of learning rate & noisy gradients

Small $\alpha$

Safe but slow.

Large $\alpha$

Dangerous; one noisy gradient can cause a huge jump.

Constant $\alpha$

Simple to implement, but $\boldsymbol\theta$ may keep bouncing near the optimum instead of settling into it.

Decreasing $\alpha$

Explore with larger steps early, settle with smaller steps later. (Learning-rate schedules are covered in depth in the Deep Learning course.)

Note: a single SGD step may temporarily increase the full training loss, because it follows one sample. The useful behaviour is the downward trend over many random updates.

3Mathematical Comparison: Batch GD vs SGD

The key idea is simple: same objective, different gradient estimator.

★ Why SGD gradients are noisy

Sample $i$'s gradient contribution is its "sample gradient". The full gradient is the average of all these contributions. SGD randomly selects one contribution, so the selected gradient is a random variable. It is unbiased (its average direction over many random choices equals the full-gradient direction), but one selected sample can still be far from that average. Outliers, class imbalance and rare patterns increase this variance, producing the zig-zag path.

★ Why noise can sometimes HELP

In non-convex models like neural networks, optimisation can get stuck in shallow local minima. SGD's randomness can help the optimiser bounce out of those flat regions. However, too much noise can also slow or prevent convergence — the learning rate and batch size have to be chosen carefully.

4Visual Intuition

  • BGD convergence path: smooth arrows towards the centre. Full gradients give stable, averaged directions.
  • SGD zig-zag path: arrows jump left and right while trending inward. Single samples produce noisy directions.
  • Loss vs epoch: BGD has a smooth curve; SGD has a bumpy downward trend.
  • Parameter-plane view: the figure above is literally the $\theta_0$-$\theta_1$ plane.
? Think & Discuss — answers
  1. Why don't Batch GD's arrows change direction wildly in the parameter plane?
    Because every arrow is the average of all $m$ samples. Individual-sample noise cancels out in the averaging, so consecutive gradients look alike and the path stays smooth.
  2. Can one "bad-looking" SGD step still be useful for training overall?
    Yes. For two reasons: (i) that step incorporated information from a real sample — the full loss may rise, but $\boldsymbol\theta$ moved in an underrepresented direction; (ii) in non-convex problems, that very jolt can knock the optimiser out of a shallow local minimum.
  3. What is the fairest x-axis for comparing the speed of two training runs — epochs, iterations, or wall-clock time?
    Wall-clock time. Epochs unfairly flatter BGD (one epoch shows one update but costs $m$ samples). Iterations unfairly flatter SGD (one iteration is cheap). Only wall-clock time captures the actual computational cost, which is what matters in practice.

The per-sample loss and its gradients

$$J_i(\boldsymbol\theta) = \tfrac12(\hat y_i - y_i)^2, \qquad \hat y_i = \theta_0 + \theta_1 x_i$$

If $e_i = \hat y_i - y_i$, the two gradient entries are:

$$\frac{\partial J_i}{\partial\theta_0} = e_i, \qquad\qquad \frac{\partial J_i}{\partial\theta_1} = e_i x_i$$
Derivation of these two gradients (chain rule)

$J_i = \frac12(\theta_0 + \theta_1x_i - y_i)^2$. Let $e_i = \theta_0 + \theta_1x_i - y_i$.

$$\frac{\partial J_i}{\partial\theta_0} = \tfrac12 \cdot 2e_i \cdot \frac{\partial e_i}{\partial\theta_0} = e_i \cdot (1) = e_i$$ $$\frac{\partial J_i}{\partial\theta_1} = \tfrac12 \cdot 2e_i \cdot \frac{\partial e_i}{\partial\theta_1} = e_i \cdot (x_i) = e_i x_i$$

This is why the $\frac12$ is put in the loss — it cancels the 2 that comes from squaring, keeping the formulas clean.

? Think & Discuss — why did the error sign flip?

Samples 2 and 4 (Steps 1–2) gave negative errors ($-4.000$, $-4.400$), but Sample 1 (Step 3) gave a positive error ($+1.400$) — even though all four points lie exactly on the line $y = 2x$!

Reason: after Steps 1–2, $\theta_1$ had moved from 0.8 to 2.56 — well above the true slope of 2. The model was now over-predicting. So in Step 3, $\hat y = 3.4$ while the actual $y = 2$ → a positive error.

And this is the real picture of SGD: because every update looks at only one sample, the optimiser oscillates back and forth around the target. Sample 4's large gradient ($-17.6$) made $\theta_1$ overshoot; the next two samples pulled it back down ($2.56 \to 2.42 \to 1.83$). This does not happen in Batch GD — there, one epoch gives just one averaged, conservative step.

6Pseudocode

Reference · Batch Gradient Descent

# Input: dataset D = {(x_i, y_i)}, learning rate alpha, epochs E
initialize theta

for epoch = 1 to E:                # outer epoch loop
    grad = 0
    for i = 1 to m:                # sample loop for ACCUMULATION
        grad = grad + gradient_J_i(theta)
    grad = grad / m                # full-batch average gradient
    theta = theta - alpha * grad   # ONE UPDATE PER EPOCH

return theta

Reference · Stochastic Gradient Descent

# Input: dataset D = {(x_i, y_i)}, learning rate alpha, epochs E
initialize theta

for epoch = 1 to E:                # outer epoch loop
    shuffle(D)                     # CRITICAL: prevents biased order
    for i = 1 to m:                # sample loop
        g = gradient_J_i(theta)
        theta = theta - alpha * g  # ONE UPDATE PER SAMPLE

return theta

★ Implementation warning

In SGD, do not accumulate gradients through the full sample loop before updating. That silently turns the code back into Batch GD.

? Spot the Difference — exactly ONE line moves

The line that moves is the $\boldsymbol\theta$ update line. In Batch GD it sits outside the sample loop (once, after the loop finishes). In SGD it moves inside the sample loop (after every sample). And one extra line gets added — shuffle(D).

7Advantages of SGD

  • Faster first update: the model changes after one sample instead of after $m$. Learning begins immediately.
  • Lower memory usage: an update only needs one sample, the current $\boldsymbol\theta$, and one gradient.
  • Better scalability: the per-update cost does not grow with $m$. That is useful when $m$ is huge.
  • Suitable for massive datasets: an approximate direction is often enough to start improving the model; waiting for the exact full gradient can be wasteful.
  • Better exploration: in non-convex problems, noisy gradients can help avoid getting stuck in flat or shallow regions.

8Limitations of SGD

  • Oscillating convergence: different samples can push $\boldsymbol\theta$ in conflicting directions.
  • Noisy updates: one outlier sample can create a large gradient jump.
  • Sensitive learning rate: $\alpha$ controls both the step size and how much the noise affects $\boldsymbol\theta$.
  • Many updates needed: each update is cheap but less informative.
  • Difficult stopping: iteration-level loss fluctuates rapidly — deciding "converged" is hard.
  • Variance across runs: different shuffles can produce different paths.

9Motivation for Mini-Batch Gradient Descent

▷ Hook

SGD solved the waiting problem but created noisy movement. If one sample is too noisy and all samples together are too expensive — what is the middle ground? Can we cut the noise without going back to scanning the whole dataset every time?

The natural answer: average a small group of samples. That is Mini-Batch Gradient Descent.

Analogy

Instead of asking the whole class or one student, ask a small group. The group's answer is less noisy than one person's, but much faster than asking everyone.

10Mini-Batch Gradient Descent

Mini-batch GD splits the shuffled dataset into small groups called mini-batches. Each update uses the average gradient over one mini-batch of size $b$.

The batch size is the compromise dial: $b = 1$ behaves like SGD, $b = m$ behaves like Batch GD, and values in between trade some speed for a steadier direction.

Updates per epoch$$\left\lceil \frac{m}{b} \right\rceil$$

Workflow

  1. Shuffle the dataset at the start of each epoch.
  2. Split it into mini-batches of size $b$.
  3. Compute the average gradient over the first mini-batch and update $\boldsymbol\theta$ immediately.
  4. Continue until every sample has been used once.
  5. Repeat for multiple epochs.

Practical points

  • Typical batch sizes: 16, 32, 64, 128, 256 — these are common choices, not requirements.
  • Why powers of two: GPU and hardware kernels handle these sizes most efficiently; the maths itself does not require them.
  • GPU utilisation: a single sample under-uses a GPU's parallel cores; a mini-batch gives it enough parallel work to stay busy.
  • Memory efficiency: only the current mini-batch needs to sit in memory for an update — not the whole dataset.

Reference · Mini-Batch Gradient Descent

# Input: dataset D, learning rate alpha, epochs E, batch size b
initialize theta

for epoch = 1 to E:                    # outer epoch loop
    shuffle(D)
    split D into mini-batches B_1, B_2, ..., B_K   # K = ceil(m / b)
    for each mini-batch B_k:           # mini-batch loop
        grad = 0
        for each (x_i, y_i) in B_k:    # sample loop INSIDE batch
            grad = grad + gradient_J_i(theta)
        grad = grad / len(B_k)
        theta = theta - alpha * grad   # ONE UPDATE PER MINI-BATCH

return theta
Worked example of $K$

If $m = 10{,}000$ and batch size $b = 10$, then $K = \dfrac{m}{b} = \dfrac{10{,}000}{10} = \mathbf{1000}$ mini-batches, i.e. 1000 updates per epoch.

Sampling NoiseThe variance introduced by estimating the full gradient from just one (or a few) samples.

Batch Size ($b$)The number of samples averaged together for one Mini-Batch GD update.

⚠ Common Mistakes

GaltiSahi Baat
"SGD only uses one sample, so the rest of the data is wasted"One update uses one sample; one epoch uses all $m$.
$m=1000$, $b=100$ → 1000 updates per epoch$\lceil m/b\rceil = 10$ updates.
Accumulating gradients in SGD and updating at the endThat silently turns the code into Batch GD. The update must sit inside the loop.
Skipping the shuffleOrdered data → biased update sequences. Shuffling at the start of each epoch is mandatory.
"The loss should drop at every SGD step"A noisy step can raise the full loss. Look at the trend, not a single point.
"More updates = faster convergence"Each update is cheaper but less accurate. Wall-clock time and stability matter too.
"Stochastic means the parameters are random"The randomness is only in sample selection; the update rule is deterministic.
Using epoch and iteration interchangeablyBGD: 1 epoch = 1 iteration. SGD: 1 epoch = $m$ iterations. Mini-Batch: 1 epoch = $\lceil m/b\rceil$ iterations.

⚡ Quick Revision

Updates per epoch

BGD: 1 · SGD: $m$ · Mini-Batch: $\lceil m/b\rceil$

Cost per update

BGD: $O(md)$ · SGD: $O(d)$ · Mini-Batch: $O(bd)$

SGD update

$\boldsymbol\theta_{t+1} = \boldsymbol\theta_t - \alpha\nabla J_{i_t}(\boldsymbol\theta_t)$,  $i_t \sim$ Uniform$\{1..m\}$

Per-sample gradient (linear reg.)

$\nabla J_i = [e_i,\ e_ix_i]^\top$ where $e_i = \hat y_i - y_i$

Batch sizes

16, 32, 64, 128, 256 — powers of two for GPU efficiency

Why shuffle?

Ordered data → biased update sequences → wrong learning signal
