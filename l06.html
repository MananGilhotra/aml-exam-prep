Stochastic & Mini-Batch
Gradient Descent

Batch GD kyun itna wait karta hai, SGD kaise ek sample se hi chal padta hai, aur Mini-Batch kaise dono ka best deta hai.

⏱ ~35 min🔁 3 dry runs 💻 3 pseudocodes✓ 10 MCQs
⚡ Ek Line Mein

Batch GD: poore dataset ka average gradient → 1 update per epoch, accurate par slow. SGD: ek random sample ka gradient → $m$ updates per epoch, fast par noisy. Mini-Batch: $b$ samples ka average → $\lceil m/b\rceil$ updates per epoch — practical compromise jo almost har real system use karta hai.

Notation used throughout

$m$number of training examples
$d$number of features (parameter dimension)
$\boldsymbol\theta$parameter vector, e.g. $(\theta_0, \theta_1)$ for a line
$\alpha$learning rate
$J_i(\boldsymbol\theta)$loss from a single training example $i$
$J(\boldsymbol\theta)$average training cost over the full dataset
Iterationone parameter update
Epochone complete pass over all $m$ training examples
$$\mathcal D = \{(x_i, y_i)\}_{i=1}^{m} \qquad\qquad J(\boldsymbol\theta) = \frac{1}{m}\sum_{i=1}^{m}J_i(\boldsymbol\theta)$$

1Revision and Motivation

▷ Hook

Batch Gradient Descent mein hum saare $m$ examples par average cost ka gradient compute karte hain aur phir $\boldsymbol\theta$ ko ek baar update karte hain. Rhythm yeh hai: saare samples scan karo → unke gradients average karo → ek baar update karo. Kya hume har ek update se pehle poore dataset ka wait karna hi padega?

Agar $m = 10{,}000{,}000$, to ek BGD epoch mein kitne parameter updates hote hain? Ek. Kya ek update 10 million samples har baar scan karne ke layak hai?

Why BGD is attractive

  • Stable direction: har sample contribute karta hai, to noisy gradients average out ho jaate hain.
  • Deterministic path: same initialization ke liye steps exactly repeatable hote hain.
  • Smooth convergence: simple convex losses par cost usually smoothly ghat-ti hai.
  • Good for small datasets: exact gradients affordable hain jab data memory mein fit ho jaye.

Disadvantages as real problems

LimitationWhy it happensWhen it's seriousExample
Waits before updateAverage over all $m$Full pass takes hoursAd clicks model (100M rows)

In saari problems ka ek hi root cause hai: BGD move karne se pehle ek exact full-data gradient demand karta hai. Exactness useful hai, par huge data ke liye yeh bohot mehnga pad sakta hai.

2Stochastic Gradient Descent (SGD)

? Think & Discuss

Full gradient compute karna mehnga hai. Sabse chhota amount of data kitna hai jo abhi bhi $\boldsymbol\theta$ ko move karne ki direction de sake? Ek single sample. Aur wo choice turant ek naya danger create kar deti hai — noise.

SGD waiting problem ka answer hai. Poore dataset se ek perfect direction maangne ki jagah, SGD ek randomly chosen example se ek quick direction maangta hai aur turant update kar deta hai.

Analogy

Batch GD koi bhi decision lene se pehle poori class ka poll leta hai. SGD ek random student se poochta hai, uske answer par turant act karta hai, phir agle se poochta hai. Koi bhi single answer galat ho sakta hai, par decisions full roll call ke baad ke bajaye instantly hote hain.

Core intuition

Har training example $\boldsymbol\theta$ ko kaise move karna chahiye iske baare mein ek chhoti si opinion deta hai. Ek single opinion biased ho sakti hai, par agar randomly select ki jaye, to bohot saari opinions full-data direction ki taraf average ho jaati hain. SGD loss function nahi badalta — wo sirf yeh badalta hai ki hum har update se pehle gradient ko kaise estimate karte hain.

The stochastic update $$i_t \sim \text{Uniform}\{1, 2, \dots, m\}, \qquad \mathbf g_t = \nabla J_{i_t}(\boldsymbol\theta_t), \qquad \boldsymbol\theta_{t+1} = \boldsymbol\theta_t - \alpha\,\mathbf g_t$$
  • $J_{i_t}$ — iteration $t$ par selected training example ka loss
  • $\nabla J_{i_t}$ — us example ke liye gradient (vector of loss slopes)
  • $\boldsymbol\theta_t$ — current parameter vector jab gradient evaluate hota hai
  • $\mathbf g_t = \nabla J_{i_t}(\boldsymbol\theta_t)$ — selected example ka gradient, current parameters par compute kiya gaya
★ Key Insight — sabse bada misconception

SGD sirf ek sample par forever train nahi kar raha! Ek update ek sample use karti hai, par ek epoch har sample use karta hai. Agar $m = 1000$, to ek SGD epoch mein 1000 updates hote hain.
$E$ full epochs ke baad SGD ne total $E \times m$ updates kiye hain — compare karo Batch GD ke mere $E$ updates se, utne hi $E$ epochs mein.

Complete SGD workflow

  1. Initialize $\boldsymbol\theta$. Learning rate $\alpha$ aur number of epochs choose karo.
  2. Har epoch ke start par, training examples ko shuffle karo.
  3. Samples ko shuffled order mein ek-ek karke visit karo.
  4. Har sample ke liye prediction, sample loss, sample gradient compute karo, aur turant $\boldsymbol\theta$ update karo.
  5. Multiple epochs ke liye repeat karo, saath-saath training (ya validation) loss trend track karte hue.
△ Warning — SHUFFLING

Real datasets often ordered hote hain (date ke hisaab se, class label ke hisaab se, region ke hisaab se). Shuffling ke bina, consecutive SGD updates true learning signal ki jagah ordering pattern ko follow kar sakti hain. Randomization SGD ko biased updates se protect karta hai!

Effect of learning rate & noisy gradients

Small $\alpha$

Safe but slow.

Large $\alpha$

Dangerous; ek noisy gradient ek huge jump cause kar sakta hai.

Constant $\alpha$

Implement karna simple, par $\boldsymbol\theta$ optimum ke paas bounce karta reh sakta hai — settle nahi hota.

Decreasing $\alpha$

Shuru mein bade steps se explore karo, baad mein chhote steps se settle karo. (Learning-rate schedules Deep Learning course mein detail mein.)

Note: ek single SGD step temporarily full training loss badha sakta hai, kyunki wo ek sample ko follow karta hai. Useful behavior hai many random updates par downward trend.

Misconceptions corrected ⭐

MisconceptionCorrection
SGD ignores most of the dataset.One update uses one sample, but one epoch uses all.

3Mathematical Comparison: Batch GD vs SGD

Key idea simple hai: same objective, different gradient estimator.

★ Why SGD gradients are noisy

Sample $i$ ka gradient contribution "sample gradient" hai. Full gradient in saare contributions ka average hai. SGD randomly ek contribution select karta hai, to selected gradient ek random variable hai. Wo unbiased hai (bohot random choices par uski average direction full-gradient direction ke barabar hai), par ek selected sample us average se bohot door ho sakta hai. Outliers, class imbalance aur rare patterns is variance ko badha dete hain, jisse zig-zag path banta hai.

★ Why noise can sometimes HELP

Neural networks jaise non-convex models mein, optimization shallow local minima mein atak sakta hai. SGD ki randomness optimizer ko un flat regions se bounce out karne mein help kar sakti hai. However, bohot zyada noise convergence ko slow ya prevent bhi kar sakta hai — learning rate aur batch size carefully choose karne padte hain.

4Visual Intuition

  • BGD convergence path: center ki taraf smooth arrows. Full gradients stable, averaged directions dete hain.
  • SGD zig-zag path: arrows left-right jump karte hain par inward trend karte hain. Single samples noisy directions produce karte hain.
  • Loss vs epoch: BGD ki curve smooth hai; SGD ki bumpy downward trend hai.
  • Parameter-plane view: upar ka figure literally $\theta_0$-$\theta_1$ plane hai.
? Think & Discuss — answers
  1. Batch GD ke arrows parameter-plane mein wildly direction kyun nahi badalte?
    Kyunki har arrow saare $m$ samples ka average hai. Individual samples ka noise average lene se cancel ho jaata hai, to consecutive gradients ek jaise hote hain aur path smooth rehta hai.
  2. Kya ek "bad-looking" SGD step overall training ke liye useful ho sakta hai?
    Haan. Do wajah se: (i) us step ne ek real sample ki information incorporate ki — full loss badh sakti hai par $\boldsymbol\theta$ ek underrepresented direction mein move hua; (ii) non-convex problems mein wahi jhatka optimizer ko shallow local minimum se bahar nikaal sakta hai.
  3. Do training runs ki speed compare karne ke liye sabse fair x-axis kya hai — epochs, iterations ya wall-clock time?
    Wall-clock time. Epochs BGD ko unfairly flatter karte hain (1 epoch mein 1 update dikhta hai par cost $m$ samples ki hai). Iterations SGD ko unfairly flatter karte hain (1 iteration sasti hai). Sirf wall-clock time actual computational cost capture karta hai, jo practically matter karti hai.

(Perfect line: the true model is $y = 2x$, i.e. $\theta_0 = 0$, $\theta_1 = 2$.)

The per-sample loss and its gradients

$$J_i(\boldsymbol\theta) = \tfrac12(\hat y_i - y_i)^2, \qquad \hat y_i = \theta_0 + \theta_1 x_i$$

If $e_i = \hat y_i - y_i$, the two gradient entries are:

$$\frac{\partial J_i}{\partial\theta_0} = e_i, \qquad\qquad \frac{\partial J_i}{\partial\theta_1} = e_i x_i$$
Derivation of these two gradients (chain rule)

$J_i = \frac12(\theta_0 + \theta_1x_i - y_i)^2$. Let $e_i = \theta_0 + \theta_1x_i - y_i$.

$$\frac{\partial J_i}{\partial\theta_0} = \tfrac12 \cdot 2e_i \cdot \frac{\partial e_i}{\partial\theta_0} = e_i \cdot (1) = e_i$$ $$\frac{\partial J_i}{\partial\theta_1} = \tfrac12 \cdot 2e_i \cdot \frac{\partial e_i}{\partial\theta_1} = e_i \cdot (x_i) = e_i x_i$$

Yahi wajah hai ki loss mein $\frac12$ rakha jaata hai — wo squaring se aane wale 2 ko cancel kar deta hai, formulas clean rehte hain.

? Think & Discuss — why did the error sign flip?

Samples 2 aur 4 (Steps 1–2) ne negative errors diye ($-4.000$, $-4.400$), par Sample 1 (Step 3) ne positive error diya ($+1.400$) — jabki saare chaar points exactly line $y = 2x$ par hain!

Reason: Steps 1–2 ke baad $\theta_1$ 0.8 se 2.56 par pahuch gaya tha — true slope 2 se kaafi upar. Model ab over-predict kar raha tha. Isliye Step 3 mein $\hat y = 3.4$ aaya jabki actual $y = 2$ tha → positive error.

Aur yahi SGD ki asli tasveer hai: kyunki har update sirf ek sample ko dekhti hai, optimizer target ke aage-peeche oscillate karta hai. Sample 4 ka bada gradient ($-17.6$) ne $\theta_1$ ko overshoot karwa diya; agle do samples ne use wapas neeche kheencha ($2.56 \to 2.42 \to 1.83$). Batch GD mein aisa nahi hota — wahan ek epoch mein sirf ek averaged, conservative step hota hai.

6Pseudocode

Reference · Batch Gradient Descent

# Input: dataset D = {(x_i, y_i)}, learning rate alpha, epochs E
initialize theta

for epoch = 1 to E:                # outer epoch loop
    grad = 0
    for i = 1 to m:                # sample loop for ACCUMULATION
        grad = grad + gradient_J_i(theta)
    grad = grad / m                # full-batch average gradient
    theta = theta - alpha * grad   # ONE UPDATE PER EPOCH

return theta

Reference · Stochastic Gradient Descent

# Input: dataset D = {(x_i, y_i)}, learning rate alpha, epochs E
initialize theta

for epoch = 1 to E:                # outer epoch loop
    shuffle(D)                     # CRITICAL: prevents biased order
    for i = 1 to m:                # sample loop
        g = gradient_J_i(theta)
        theta = theta - alpha * g  # ONE UPDATE PER SAMPLE

return theta

★ Implementation warning

SGD mein, full sample loop ke through gradients accumulate mat karo update se pehle. Wo silently code ko wapas Batch GD bana deta hai.

? Spot the Difference — exactly ONE line moves

Line jo move karti hai wo hai $\boldsymbol\theta$ update line. Batch GD mein wo sample loop ke bahar hai (loop khatam hone ke baad, ek baar). SGD mein wo sample loop ke andar chali jaati hai (har sample ke baad). Aur ek extra line add hoti hai — shuffle(D).

7Advantages of SGD

  • Faster first update: Model $m$ samples ke baad nahi, ek sample ke baad badal jaata hai. Learning turant shuru hoti hai.
  • Lower memory usage: Ek update ke liye sirf ek sample, current $\boldsymbol\theta$, aur ek gradient chahiye.
  • Better scalability: Per-update cost $m$ ke saath grow nahi karti. Jab $m$ huge ho to yeh useful hai.
  • Suitable for massive datasets: Model improve karna shuru karne ke liye ek approximate direction often kaafi hai; exact full gradient ka wait karna wasteful ho sakta hai.
  • Better exploration: Non-convex problems mein noisy gradients flat ya shallow regions mein atakne se bachne mein help kar sakte hain.

8Limitations of SGD

  • Oscillating convergence: Alag samples $\boldsymbol\theta$ ko conflicting directions mein push kar sakte hain.
  • Noisy updates: Ek outlier sample ek large gradient jump create kar sakta hai.
  • Sensitive learning rate: $\alpha$ step size aur $\boldsymbol\theta$ par noise ka asar dono control karta hai.
  • Many updates needed: Har update sasti hai par kam informative.
  • Difficult stopping: Iteration-level loss rapidly fluctuate karti hai — "converged" decide karna mushkil.
  • Variance across runs: Alag shuffles alag paths produce kar sakte hain.

9Motivation for Mini-Batch Gradient Descent

▷ Hook

SGD ne waiting problem solve kar di par noisy movement create kar di. Agar ek sample bohot noisy hai, aur saare samples ek saath bohot expensive hain — to middle ground kya hai? Kya hum noise cut kar sakte hain bina har baar poora dataset scan kiye?

Natural answer: samples ke ek chhote group ka average lo. Yahi Mini-Batch Gradient Descent hai.

Analogy

Poori class ya ek student se poochne ki jagah, ek chhote group se poocho. Group ka answer ek insaan se kam noisy hai, par sabse poochne se bohot faster hai.

10Mini-Batch Gradient Descent

Mini-batch GD shuffled dataset ko chhote groups mein todta hai jinhe mini-batches kehte hain. Har update ek mini-batch (size $b$) par average gradient use karti hai.

Batch size compromise dial hai: $b = 1$ SGD ki tarah behave karta hai, $b = m$ Batch GD ki tarah, aur beech ki values speed ko steadier direction ke liye trade karti hain.

Updates per epoch$$\left\lceil \frac{m}{b} \right\rceil$$

Workflow

  1. Har epoch ke start par dataset shuffle karo.
  2. Use size $b$ ke mini-batches mein split karo.
  3. Pehle mini-batch par average gradient compute karo aur $\boldsymbol\theta$ immediately update karo.
  4. Continue karo jab tak har sample ek baar use na ho jaaye.
  5. Multiple epochs ke liye repeat karo.

Practical points

  • Typical batch sizes: 16, 32, 64, 128, 256 — common choices hain, compulsory nahi.
  • Why powers of two: GPU aur hardware kernels in sizes ko sabse efficiently handle karte hain; maths khud demand nahi karti.
  • GPU utilization: ek single sample GPU ke parallel cores ko under-use karta hai; ek mini-batch use busy rakhne ke liye kaafi parallel work deta hai.
  • Memory efficiency: ek update ke liye sirf current mini-batch ko memory mein rakhna padta hai — poora dataset nahi.

Reference · Mini-Batch Gradient Descent

# Input: dataset D, learning rate alpha, epochs E, batch size b
initialize theta

for epoch = 1 to E:                    # outer epoch loop
    shuffle(D)
    split D into mini-batches B_1, B_2, ..., B_K   # K = ceil(m / b)
    for each mini-batch B_k:           # mini-batch loop
        grad = 0
        for each (x_i, y_i) in B_k:    # sample loop INSIDE batch
            grad = grad + gradient_J_i(theta)
        grad = grad / len(B_k)
        theta = theta - alpha * grad   # ONE UPDATE PER MINI-BATCH

return theta
Worked example of $K$

If $m = 10{,}000$ and batch size $b = 10$, then $K = \dfrac{m}{b} = \dfrac{10{,}000}{10} = \mathbf{1000}$ mini-batches, i.e. 1000 updates per epoch.

Update 2 (solved): $B_2$ contains only Sample 3 ($x = 3$, $y = 6$).

  1. Prediction $$\hat y_3 = 0.467 + 1.400(3) = 0.467 + 4.200 = \mathbf{4.667}$$
  2. Error $$e_3 = \hat y_3 - 6 = 4.667 - 6 = \mathbf{-1.333}$$
  3. Average gradient (only one sample, so the average is itself) $$\bar{\mathbf g}_2 = \begin{bmatrix}-1.333\\ -1.333 \times 3\end{bmatrix} = \begin{bmatrix}\mathbf{-1.333}\\ \mathbf{-4.000}\end{bmatrix}$$
  4. Update $$\boldsymbol\theta^{(2)} = \begin{bmatrix}0.467\\ 1.400\end{bmatrix} - 0.1\begin{bmatrix}-1.333\\ -4.000\end{bmatrix} = \begin{bmatrix}\mathbf{0.600}\\ \mathbf{1.800}\end{bmatrix}$$
  5. Number of mini-batches in the epoch $$K = \left\lceil \frac{m}{b} \right\rceil = \left\lceil \frac{4}{3} \right\rceil = \mathbf{2}$$
    Last batch mein sirf 1 sample hai — yeh bilkul normal hai. Ceiling function isliye use hota hai: koi bhi leftover sample apna chhota batch banata hai, discard nahi hota.

📖 Key Terms

TermDefinition
Batch Gradient DescentUpdates parameters using the exact average gradient over the entire dataset.
Stochastic GD (SGD)Updates parameters immediately using the gradient of a single randomly chosen sample.
Mini-Batch GDUpdates parameters using the average gradient over a small group ($b$) of samples.
EpochOne complete pass through all $m$ training examples.
IterationOne parameter update step.
ShufflingRandomizing the order of the dataset before each epoch to prevent biased learning patterns.
Sampling NoiseThe variance introduced by estimating the full gradient from just one (or a few) samples.
Learning Rate ($\alpha$)The step size that scales the gradient before it is subtracted from $\boldsymbol\theta$.
Batch Size ($b$)The number of samples averaged together for one Mini-Batch GD update.

⚠ Common Mistakes

GaltiSahi Baat
"SGD sirf ek sample use karta hai, baaki data waste ho jaata hai"Ek update ek sample use karti hai; ek epoch saare $m$ use karta hai.
$m=1000$, $b=100$ → 1000 updates per epoch$\lceil m/b\rceil = 10$ updates.
SGD mein gradients accumulate karke end mein update karnaWo code ko silently Batch GD bana deta hai. Update loop ke andar hona chahiye.
Shuffling skip kar denaOrdered data → biased update sequences. Har epoch ke start par shuffle mandatory hai.
"Loss har SGD step par girni chahiye"Noisy step par full loss badh sakti hai. Trend dekho, single point nahi.
"Zyada updates = faster convergence"Har update sasti par kam accurate hai. Wall-clock time aur stability bhi matter karte hain.
"Stochastic ka matlab parameters random hain"Randomness sirf sample selection mein hai; update rule deterministic hai.
Epoch aur iteration ko interchange karnaBGD: 1 epoch = 1 iteration. SGD: 1 epoch = $m$ iterations. Mini-Batch: 1 epoch = $\lceil m/b\rceil$ iterations.

⚡ Quick Revision

Updates per epoch

BGD: 1 · SGD: $m$ · Mini-Batch: $\lceil m/b\rceil$

Cost per update

BGD: $O(md)$ · SGD: $O(d)$ · Mini-Batch: $O(bd)$

SGD update

$\boldsymbol\theta_{t+1} = \boldsymbol\theta_t - \alpha\nabla J_{i_t}(\boldsymbol\theta_t)$,  $i_t \sim$ Uniform$\{1..m\}$

Per-sample gradient (linear reg.)

$\nabla J_i = [e_i,\ e_ix_i]^\top$ where $e_i = \hat y_i - y_i$

Batch sizes

16, 32, 64, 128, 256 — powers of two for GPU efficiency

Why shuffle?

Ordered data → biased update sequences → wrong learning signal
